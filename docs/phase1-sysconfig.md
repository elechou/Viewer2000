## 1. cpu1's SysConfig: two LED instances (mostly configured, only the Core Select swap left)

You've already configured `LED_CPU1` (LED4 red) and `LED_CPU2` (LED5 green) with the board-components LED module; the $hardware binding + initial value 1 are both correct. **One thing left to fix: Core Select is reversed** —

| Instance | Current | Should be |
|---|---|---|
| `LED_CPU1` (red, used by CPU1) | Core Select = CPU2 ← wrong | **CPU1** (default) |
| `LED_CPU2` (green, used by CPU2) | unset (default CPU1) | **CPU2** |

Symptom if not fixed: the red LED never lights (CPU1 can't write a data register that's been assigned to CPU2); the green LED can still light via the `GPIO_setControllerCore` fallback in `runtime/v2k_main.c`, but the formal place for the ownership assignment is here.

Notes:

- both LEDs are **active-low** (this board is the opposite of most LaunchPads), initial value 1 = off at power-up;
- the board.h macros generated by the board-components LED module carry a `_GPIO` suffix (`LED_CPU1_GPIO` / `LED_CPU2_GPIO`), and `runtime/v2k_main.c` references them accordingly — **don't rename the instances**;
- avoid GPIO42/43 (XDS110 serial backchannel, needed in Phase 3.5).

## 4. Dual-core debug session (order is critical, don't change it)

**Prerequisite (one-time)**: if on-chip flash has had old firmware burned in, erase it first — any unexpected reset (watchdog, NMI watchdog, XRS) makes CPU1 boot from flash into the old firmware, with the symptom "runs away to a no-source address + CPU2 pushed back into reset" (measured 2026-06-12 in BRINGUP.md, PC lands at 0x081A3A). Action: after connecting CPU1, Tools → On-Chip Flash → check Bank0–2 → Erase. During bring-up, also setting the S3 left DIP to 0 (wait-boot) as a double safeguard is recommended.

1. Launch the target configuration (manually connect after launch, **do not directly Debug As auto-connect-all** — the auto flow goes to connect CPU2 while CPU1 is still stopped at main, but CPU2's reset is only released after CPU1 runs past `Device_bootCPU2`, so the CPU2 side reports a string of *"Device is held in reset"* / GEL / load failures. Seeing this symptom = wrong order; remedy: Resume CPU1 → then Connect CPU2 → Load → Resume, no need to restart the session. Permanent fix: disable the CPU2 core's auto program load in the Debug Configuration);
2. **Connect CPU1 → Load `cpu1.out` → Resume.** CPU1 runs to `IPC_sync` and blocks waiting for CPU2 — at this point the red LED isn't blinking and it looks hung, **normal**;
3. **Connect CPU2 → Load `cpu2.out` → Resume.** ⚠️ Reason for the order: GS4 belongs to CPU1 at power-up, and GS4 is only handed to CPU2 after CPU1 runs past `MemCfg_setGSRAMControllerSel`; if you load CPU2 first, its .out load into GS4 fails or doesn't verify;
4. Expected: **red LED4 blinks at 1 Hz, green LED5 blinks at 2 Hz**;
5. Either core stopped in the `ESTOP0` dead loop = `v2k_assert_layout` self-check failed (.cmd mismatched v2k_memmap.h), or the CPU2 contract-version handshake failed (look at `g_handshake_state`); send me.
