*左 — **LAUNCHXL-F28P65X + BOOSTXL-DRV8323RX** パワーステージで PMSM を駆動、
AS5600 エンコーダ付き。右 — 同じボードでオープンループ V/f を回し、**Scope2000**
にリアルタイムストリーミング：電気角、三相電流、三相 PWM デューティ —
全トレースが `control()` の中のプレーン C 変数そのもの。*

モーター制御をやったことがある人なら分かると思うが、C2000 で FOC を動かそうとすると、
ブート・クロック・ピンマックス・ePWM→ADC→EOC チェーン・フォルト保護・デュアルコア
通信を設定するだけでだいたい気が狂う。そこまでやって、ようやく制御アルゴリズムを
書き始められる。観測も面倒で、CCS の Graph ウィンドウは使えなくはないが柔軟性に欠け、
マルチチャンネル波形を出すのにまた一苦労する。

Viewer2000 がやることはシンプルで、**この低レベル処理を全部引き受ける**。`setup()`
と `control()` をフラットな I/O 構造体に対して書く。それがアプリケーションの全体像だ。
同時に、コンパニオンの [Scope2000](https://github.com/elechou/Scope2000) ホスト
ビューアで、中の変数を制御ループレートでリアルタイムに観測・変更できる — 再フラッシュ
不要、CCS ウィンドウ設定不要、変数名はファームウェアからデバイスに自動で焼き込まれて
いる。プロジェクトのソースコードが一切入っていない PC にボードを挿して、
[Scope2000](https://github.com/elechou/Scope2000) だけでモーターを制御することすら
できる。

## ハイライト

- **Arduino スタイルの制御ループ** — アプリ全体がグローバル `v2k_io` に対する
  `setup()` + `control()`。ボイラープレートなし、レジスタ操作なし。
- **ライブ観測、再フラッシュ不要** — ビルド時にプレーン C 変数名を自動でファーム
  ウェアに焼き込み、Scope2000 が名前で直接表示。ピン・プロット・ライブ書き込み
  まで可能、値を変えてそのまま続行。
- **構造的に決定的** — プラットフォームが ePWM→ADC→EOC チェーンを所有し、1 周期に
  1 回 `control()` を呼ぶ。1 サンプル = 1 制御周期で、「このサンプルはどの周期の
  ものか」という問題は存在しない。
- **保護は無効化できない** — ハードウェアトリップ (TZ/CMPSS) とフォルトステート
  マシンはコードの*下*にある、コードの*中*ではない。`control()` が暴走しても、
  PWM はちゃんと止まる。
- **デュアルコア分離** — CPU1 が制御、CPU2 が通信。通信側がスタック・切断・
  クラッシュしても、制御ループは回り続ける。
- **TI 公式エコシステムをそのまま使える** — 純粋 C なので、C2000Ware・
  MOTORCONTROL-SDK・DCL をそのまま include して使える。TI 公式サンプルと全く
  同じ使い方。
- **トリガースナップショット & CSV** — プリトリガー履歴キャプチャと簡単な CSV
  エクスポート。

## Arduino のようにモーター制御を書く

アプリ全体は 2 つの関数と 1 つのグローバル I/O 構造体だ：

```c
#include "v2k.h"

// プレーン C グローバル変数。ビルド時にファームウェアに自動焼き込み、
// Scope2000 が名前で直接表示 — ピン・ウォッチ・スコープ・ライブ書き込み可能、
// 再フラッシュ不要。
float    duty   = V2K_DUTY_NEUTRAL;   // 0.50 = ニュートラル
uint16_t ia_raw;

void setup(void) {
    // リセットごとに 1 回実行、control() の前。
    duty = V2K_DUTY_NEUTRAL;
}

void control(void) {
    // 制御周期ごとに実行（例：20 kHz）、ADC フレームがクローズした瞬間に入る。
    ia_raw = v2k_io.adc.ia_raw;          // コヒーレントな時間整列サンプル
    v2k_pwm_apply(duty, duty, duty);     // 三相デューティを送信
}
```

以上。説明が要るのは 3 つだけ：

- **`v2k_io.adc`** — この制御周期で変換完了済みの ADC 生データフレーム。相電流・
  相電圧・バス電圧が全部入っている。
- **`v2k_io.sys`** — プラットフォームティック、スケジュールフラグ（`V2K_DUE_1KHZ`
  / `V2K_DUE_100HZ` — 「この tick で低速タスクを回すべきか」を知るためのもの）、
  状態、フォルトコード。
- **`v2k_pwm_apply(a, b, c)`** — 三相デューティを送信。暗黙の出力はない。
  `control()` が return した後にプラットフォームがこっそり apply するようなことは
  ない。出力は常に自分の明示的な呼び出し。

この `control()` は Arduino の `loop()` とちょっと違う点がある。Arduino の `loop()`
は割り込みが来ない限り CPU を占有し続けるフリーランニングのスーパーループだ。
こちらの `control()` は 20 kHz の ISR 本体で、モーター制御においては「この関数が
割り込みサービスルーチンそのものである」ということこそが本質的に重要だからだ。

動作例 — 電流オフセットキャリブレーションと周波数スルー付きの低エネルギーオープン
ループ V/f — が [`cpu1/app/user.c`](cpu1/app/user.c) に入っているので、
そのままコピーして改造できる。

## ハードウェア

すぐに使えるサポート対象ハードウェアは TI の公開評価キット（ページ上部の写真）：

| パーツ | 何か |

| **LAUNCHXL-F28P65X** | デュアルコア C2000 LaunchPad（制御 MCU） |

## ⚠️ 安全上の注意

このプラットフォームが駆動するのは本物のパワーステージで、回すのは本物のモーターだ。
大電流を流せるし、危険な電圧をスイッチングする。

- 新しいコードは**必ず**低バス電圧・低変調度・電流制限付き電源で立ち上げる。
  正常動作を確認してからエネルギーを上げること。
- 回転部品から離れる。モーターは機械的に固定する。
- 内蔵保護（過電流トリップ、フォルトラッチ）は**セーフティネット**であって、
  電流リミッタを省略していい理由ではない。
- 自分のハードウェア、自分の配線、自分のモーター — 安全は自己責任。

## クイックスタート

[Code Composer Studio](https://www.ti.com/tool/CCSTUDIO)、TI の C2000Ware
MOTORCONTROL-SDK、上記の評価キット、そして
[Scope2000](https://github.com/elechou/Scope2000) ホストビューアが必要。

1. **ビルド。** `cpu1/` と `cpu2/` を CCS にインポートして両方ビルド（高速
   イテレーションなら `RAM` 構成、スタンドアロンブートなら `FLASH`）。ビルドが
   自動的に SysConfig を実行し、ユーザー変数ディスクリプタを焼き込む。特別な設定
   は不要。
2. **ロード・実行。** ボード搭載の XDS110 で接続し、両コアをロードして実行。
3. **波形を見る、パラメータを調整する。** Scope2000 を起動し、ボードの XDS110
   仮想 COM ポートに接続。変数が自動的に出てくる — ピン・スコープ・ライブ書き
   込み、好きにいじれる。
4. **自分のものにする。** [`cpu1/app/user.c`](cpu1/app/user.c) の `control()` を
   編集、リビルド、リロード — 次の列挙で新しい変数が Scope2000 に出てくる。

ハードウェア検証済みのフル立ち上げ手順は [`BRINGUP.md`](BRINGUP.md)、各フェーズの
設計ドキュメントは [`docs/`](docs/) にある。

## 4 層アーキテクチャ

Viewer2000 のコードは 4 層に分かれている。重要な境界は **L1 と L2 の間**：
プラットフォームが L0–L1 を持ち、ユーザーが L2–L3 を持つ。

| 層 | 場所 | やること |
|:--:|---|---|
| **L3** | `cpu1/app/` | `setup()` / `control()`、アプリケーション状態 |
| **L2** | 自前の制御モジュール | 制御数学とモーターセマンティクス：C2000Ware MOTORCONTROL-SDK、DCL、手書き、または Simulink 生成の C |
| **L1** | `cpu1/runtime/` | ISR スケジューリング、制御ステートマシン、保護ポリシー、パラメータ/ディスクリプタ、RAM スコープ |
| **L0** | `cpu1/board/` | ブート、メモリマップ、ピンマックス、ePWM/ADC/CMPSS/TZ/X-BAR、DRV8323RS & AS5600 ドライバ — C2000Ware driverlib ベース |

もう 1 つのコアが横で動いている：**CPU1 が制御ドメイン、CPU2 が通信ドメイン**
（今は SCI、将来はより高速な EtherCAT）。この分割はフォルトドメイン*と*タイム
ドメインの隔離が目的で — 通信側が落ちても、制御ループの決定性には影響しない。

### どの層をいじるか？

普通は、目的に合った 1 層だけ触ればいい：

| やりたいこと | いじる場所 | 層 |
|---|---|:--:|
| 制御アルゴリズムを動かす（FOC / V/f / 自前ループ） | `cpu1/app/user.c` — `setup()` / `control()` | **L3** |
| 特定の制御ライブラリを持ち込む | 自前の制御モジュール：MOTORCONTROL-SDK / DCL を取り込むか、`app/` に直接書く | **L2** |
| 保護閾値の調整、高度なタイミング/スケジューリング | `cpu1/runtime/` | **L1** |
| ボード・配線・センサの変更 | `cpu1/board/`（ボードプロファイル） | **L0** |

大半のユーザーは L2–L3 だけで完結する。L0 はボードや配線が変わったときのワンタイム
適応で、L1 はほぼ触る必要がない。

## 誰向けか

1. **研究者** — 制御アルゴリズムだけに集中したい、チップの立ち上げやペリフェラル
   設定に時間を使いたくない人。
2. **学生** — FOC やモーター制御を学んでいて、自分が書いた数式が画面上で実際の
   電流波形を動かすのを見たい人。
3. **組み込み初心者** — C2000 でモーターを回したいが、初期化コード・レジスタ設定・
   保護パイプラインにいきなり埋もれたくない人。
4. **素早い評価が必要な人** — 制御則を差し替えて A/B 比較、新しいモーターを
   評価 — 当日中に結果が欲しい人。
5. **教員・TA** — 再現性のある教育環境が必要で、コアコードが短く読みやすく、
   全ベンチで同一であってほしい人。
6. **アルゴリズムエンジニア** — Simulink 生成や手書きの制御 C コードを製品 BSP に
   投入する前に、実ボード上で検証したい人。

## 誰向けでないか

1. **C2000 そのもの / C2000Ware SDK を深く学びたい人。** ここは正直まだ道半ばだ。
   C2000Ware や MOTORCONTROL-SDK との互換性はできるだけ維持しているので、公式
   サンプルと同じように公式 API を呼べる。ただ、ランタイムが**一部の安全保護を
   強制**しているため、場合によっては公式 API が「効かない」ことがある — タイミング・
   出力リリース・割り込み・保護のオーナーシップがプラットフォーム側にあるためだ。
   このギャップは継続的に縮小中で、互換性は改善し続けている。
2. **STM32 などの非 C2000 ユーザー、非デュアルコアも不可。** プラットフォームは
   最初からデュアルコア C2000 のフォルト/タイムドメイン分離を前提としている。
   他の DSP ファミリーへのポーティングはプロジェクト構造の大幅な変更が必要に
   なりそうなので、新しい DSP ターゲットは別リポジトリになる可能性が高い。
3. **モーター*製品*を作ろうとしている人。** プラットフォームで制御アルゴリズムを
   動かして検証するところまではできる — だが制御アルゴリズムは往々にして製品の中で
   *一番小さい*部分だ。プラットフォームが代わりにやってくれている IO・初期化・
   BSP こそ、製品化するときに全部やり直す必要がある部分で、その移行は非常につらい。

## FAQ

**なぜ CPU1 がサンプリングするのか — 自分で ADC を読めばよくないか？**
> **タイミングの統一性**のため。プラットフォームが ePWM→ADC SOC→EOC チェーンを
> 所有し、ADC フレームの変換が完了してから `control()` を呼ぶ。各サンプルは
> 20 kHz 制御周期の**最初**の固定ポイントで取得される。そして `control()` は
> **サンプリング完了直後に入る**ので、`v2k_io.adc` インターフェースは常に信頼
> できる — 固定周期で ADC サンプルを取り、この tick の変換が確実に完了した値だ。
> 制御則が見るのは常にコヒーレントで時間整列されたスナップショットであり、
> 「ループのどこかのランダムな位置で ADC を読んだ値」ではない。

**CPU1 の算力がタイトなのに、なぜスコープサンプリングも CPU1 に置くのか — CPU2 に
オフロードすればいいのでは？**

> サンプリングが**時間的に決定的**でなければならないから。CPU2 がコアをまたいで
> CPU1 の変数を読みに行くと、各読み取りが前回の制御 tick からちょうど 1 割り込み
> 後に着地する保証が何もない。CPU2 が tick を見逃す、同じ tick を 2 回読む、
> あるいはもっと悪いことに 2 つの隣接 tick の値を混ぜて 1 tick として
> ホストに渡す、ということが起こりうる。制御結果を正確に観測する必要がある場合、
> これは受け入れられない。
>
> CPU1 の制御 ISR 内部でサンプリングすれば、全チャンネルが自然に同一 tick に
> なる：1 サンプル、1 制御周期、クリーン。
>
> とはいえ CPU1 のサイクルが貴重なのは事実だ。超高速運転（100 kHz 以上）では、
> 協調的に分割できるスコープ処理を CLA や CPU2 に移す計画がある。tick 精度は
> 不要だが CPU1 の最大ヘッドルームが欲しい場合、将来的にはスコープ機能を
> CPU1 から完全に切り離すパスも出てくるだろう。

**Arduino も C++ なのに — なぜ純粋 C なのか？**

> この文脈では、C++ のメリットが面倒さを上回っていないから：
>
> - **可観測性。** メインのデバッグインターフェースは CCS Expressions/Graph と
>   Scope2000 のウォッチツリーで、フラットな C 構造体を直接読む。C++ の name
>   mangling、テンプレート、private メンバーは map ファイルと watch ウィンドウで
>   障害になる。
> - **公式コードをそのまま使う。** C2000Ware・MOTORCONTROL-SDK・DCL は全部
>   純粋 C。C のままなら include して使うだけ、TI 公式サンプルと全く同じ —
>   `extern "C"` で包む必要なし、混合コンパイルのリンク問題と戦う必要なし。
> - **CLA オプション。** CLA は C サブセットのみ受け付ける。高速ループを C に
>   保てば、将来 CLA に移すオプションが残る。
> - **ターゲットユーザー。** 対象 — 初心者とモーター制御研究者 — は普段から C を
>   書いており、今後の仕事もおそらく TI の C2000Ware エコシステムが相手になる。
>
> プラットフォームの複雑さが C の限界を超える日が来たら、この決定は見直す。
> ただ現時点では、TI 公式エコシステムが include 1 つで手に入る最短パスが C だ。

## 現在のステータス

Viewer2000 は**活発に開発中**で、現在は単一のハードウェアターゲット上で動作して
いる。エンドツーエンドで動作済み：デュアルコアブートと IPC、ハードウェア保護、
マルチレートスケジューリング、RAM スコープ、アトミックパラメータトランザクション、
SCI ストリーミングから Scope2000、オープンループ V/f 初回回転アプリケーション。

次のステップ：

- 同じ `setup()`/`control()` インターフェース上の閉ループ FOC ユーザーサンプル。
- **EtherCAT** トランスポートレイヤー（プロトコルはパイプの中にある — 物理層を
  入れ替えてもサービスモデルは変わらない）。
- L0 ボードレイヤーの強化、新ターゲットが単一層の変更で済むようにする。
